# Research: Cypherdoc Injection Grammar

## Decision 1: Injected grammar receives full node text, including delimiters

**Decision**: The cypherdoc grammar must match `/**` as its opening token and `*/` as its
closing token.

**Rationale**: Tree-sitter passes the full text of the matched injection node to the injected
grammar. The `doc_comment` token in `tree-sitter-cypher` captures `/** ... */` in its entirety,
so the cypherdoc grammar receives the complete string — delimiters and all. The grammar's root
rule must account for them.

**Alternatives considered**: Using `#set! injection.include-children false` or offset markers
to strip the delimiters. Rejected because `doc_comment` is a single terminal token (not a rule
with named children), so there are no children to exclude, and the offset API is fragile.

---

## Decision 2: Decorative ` * ` line prefixes handled via `extras`

**Decision**: Use the `extras` array to declare a pattern that skips the decorative asterisk
prefix on each line:

```js
extras: $ => [
  /[ \t]+/,
  /\n[ \t]*\*[ \t]?/,
]
```

**Rationale**: The pattern `\n[ \t]*\*[ \t]?` matches a newline followed by optional
horizontal whitespace, a literal `*`, and optional trailing space or tab — exactly the
` * ` decoration on each line. Declaring this as an extra means it is automatically skipped
between any two tokens in any rule, without needing to embed it in every production.

The `[ \t]+` extra handles horizontal whitespace within a line (e.g., spaces between the
param name and the `-` separator).

**Alternatives considered**: Treating line prefixes as explicit tokens in each rule (e.g.,
`seq(line_prefix, content)`). Rejected because it would clutter every rule and require
lookahead at every line boundary.

**Risk**: The pattern `\n[ \t]*\*[ \t]?` matches any lone `*` that appears after a newline
with whitespace. Inside a `tag_description` or `description`, a line like `\n * see above`
would have the ` * ` eaten. This is acceptable — the description text after the decoration
is what we want.

## Decision 3: `array_marker` is a two-character atomic token `"[]"`

**Decision**: Define `array_marker` as the literal string `"[]"` (two characters), not as
two separate bracket tokens.

**Rationale**: In `{[col: type][]}`, the sequence of characters at the end is `][]`. The
tree-sitter lexer uses maximal-munch (longest-match). Because `][]` (three characters) is
not registered as any token, the lexer matches `]` (closes the `tuple_type`), then matches
`[]` (two chars) as the `array_marker`. This is unambiguous because the only place `[` can
appear after a `]` in a type annotation is as the start of the array marker.

**Alternatives considered**: Representing array_marker as `seq('[', ']')`. Rejected because
this would require the parser to see two separate bracket tokens and risks confusion with the
tuple's opening `[` in an error-recovery context.

---

## Decision 4: `description` is a sequence of text lines, not a single regex

**Decision**: The `description` rule matches one or more lines of prose text that do not
start with `@`. Each line is captured as free text up to the end of the line:

```js
description: $ => repeat1($.description_line),
description_line: $ => /[^@\n*][^\n]*/,
```

**Rationale**: A single regex spanning multiple lines would fight with the extras system.
Matching line-by-line lets the `\n[ \t]*\*[ \t]?` extra strip the decoration at each
line boundary, leaving each `description_line` as the bare prose content.

**Alternatives considered**: One large regex for the whole description block. Rejected
because tree-sitter extras operate between tokens, not within them — a multi-line regex
would swallow the decorations that the extras are supposed to strip.

## Decision 5: Subdirectory grammar layout

**Decision**: Minimum viable file set for `tree-sitter-cypherdoc/`:

```
tree-sitter-cypherdoc/
  grammar.js        (source of truth)
  package.json      (name: "tree-sitter-cypherdoc", type: "module")
  tree-sitter.json  (registers language name "cypherdoc")
  queries/
    highlights.scm
    tags.scm
  test/
    corpus/
```

The `src/` directory is generated by `tree-sitter generate` and is not hand-authored.
Bindings (Node.js, Rust, Python, etc.) are deferred — they are generated scaffolding and
not needed until the grammar is published as a standalone package.

`tree-sitter.json` must set `"injection-regex": "cypherdoc"` so editors resolve the
injection language name to this grammar.

**Alternatives considered**: Including all binding scaffolding from day one. Rejected
because it adds noise without value while the grammar is under active development in a
subdirectory. Extraction to a standalone repo with full bindings is a natural later step.

## Decision 6: Constitution gates adapted for cypherdoc

The existing project constitution references the openCypher BNF (Fidelity gate) and the
openCypher TCK (TCK gate). Neither applies to cypherdoc, which has no upstream spec.

**Adapted gates for cypherdoc**:

| Gate | Cypherdoc interpretation |
|---|---|
| **Fidelity** | Every rule traces to a tag definition in `proposals/cypherdoc-injection.md` |
| **Dual-coverage** | ≥1 positive AND ≥1 negative corpus test per grammar rule |
| **TCK analog** | `tree-sitter parse` on all five `cypher/*.cypher` example files reports zero ERROR nodes in the `doc_comment` subtree |

A constitution amendment is not required — these are scope-specific interpretations of the
existing principles, not changes to the principles themselves.
